This page explains how the platform is put together — the layers, the flows, the two blockchains, and the governance that holds it all together.

01

Four principles that explain everything else

Every design decision in the platform — where data lives, why there are two chains, why the schema is version-controlled — follows from these four beliefs.

🗄️

The schema is the product

Dashboards, spreadsheets, agents, and blockchain views are all just interfaces. The durable asset is the canonical PostgreSQL schema (344+ versioned migrations), the metric dictionary, verification logic, and API contracts.

⛓️

Web3 is a proof layer, not source of truth

Operational and financial truth lives in PostgreSQL. Blockchain supplies proofs, coordination, and public verifiability — attestation UIDs, transaction hashes, and timelocked governance.

🤝

Humans and AI agents share the same objects

AI agents reach the platform through the same governed objects, permissions, and audit trails as people (via Directus MCP, the gateway, and the agent task catalogue) — not through a parallel back door.

🔒

Private evidence stays off-chain by default

Public surfaces store only hashes, CIDs, attestation UIDs, chain labels, and tx hashes. Raw private MRV payloads (photos, field data) remain in controlled off-chain storage. Merkle-based selective disclosure lets you prove a fact without revealing the evidence.

02

The big picture: six layers, one flow

Data enters through ingestion, is normalized into the data plane, is served through API layers to stakeholders (human and AI), and — for the small, public slice — is anchored on-chain as proofs. The service plane in the middle is where all domain logic lives.

💡 Read the diagram from the bottom up for data flow: ingestion → data plane → services → APIs → stakeholders, with a thin slice of it continuing down to blockchain proofs. Read it top-down for how people and agents reach the data.

The schema itself is version-controlled: schemas/postgres/ (344 migrations, source of truth), schemas/directus/ (API-layer snapshots), schemas/clickhouse/ (event schemas), and schemas/seeds/ (EAS schemas, metric definitions, governance config). Migrations are ordered and checksummed — you never edit an applied migration; you add a new one.

05

Two chains, one proof layer

A common confusion: why two blockchains? Because they do two different jobs. Celo carries attestations (verified claims about reality — "this harvest happened, this MRV data is true"). Gnosis Chain carries coordination infrastructure (the guild protocol, reputation points, credit tokens, and the price oracle). The legacy Moloch v2 DAO on Gnosis remains the treasury governance layer; Colony is the execution/reputation layer.

06

On-chain vs off-chain: what goes where

The privacy design is a strict separation: private substance stays off-chain, public proof goes on-chain. The raw payload never leaves controlled storage — only deterministic references to it do.

Off-chain (private)On-chain (public)
Evidence Raw photos, MRV payloads, field data in the evidence vault Hashes · CIDs · attestation UIDs · chain labels · tx hashes
Truth Full canonical records in PostgreSQL, analytics in ClickHouse Attestations asserting verified facts (gated by resolver)
Identity & credit Agent metadata, task catalogue (marketplace identity/escrow is external) KGP reputation points, credit token balances & burns
Privacy tool — Merkle-based KokonutSelectiveDisclosure: prove a fact without revealing evidence
🎯 Why? Farmers' operational data (yields, soil, finances) is commercially sensitive. Publicly proving "verified data exists and was reviewed" delivers credibility to funders and certifiers while keeping the substance private — that's the entire point of the hash-up / data-down pattern.
07

Security & the upgrade ceremony

Access control is layered: Directus roles for operations, governance roles for the DAO-style layer, and on-chain authority for contract upgrades. Every mutation is audited.

👥

Directus roles

Administrator, Field Worker, Supervisor, Manager, Finance, Analyst — with per-collection, per-action, per-field permissions, plus row-level filter rules. Sensitive fields are hidden per role.

🧭

Governance roles

stakeholder-steward, circle-steward, evidence-custodian, consent-custodian, grievance-owner, ecological-proxy-steward, market-relationship-owner, governance-facilitator, governance-recorder — defined in governance_circle / governance_role.

📜

Audit trail

All mutations land in audit_log. Agents operate under the same permissions and audit trails as humans — there is no privileged agent bypass.

⏱️

Timelocked upgrades

KGP upgrades follow a staged ceremony (below) so that no single key can change contract logic unilaterally.

The same principle applies to carbon retirement: quantity is reserved atomically, and the final balance mutation / certificate use requires an independent human confirmation. Agent write paths (proposal submission, execution, ragequit, shaman calls) are out of scope for the read-first governance adapters and must route through a human-approved Agent/Governor flow.

08

Farms as configurable containers

The platform treats each farm or project like a Docker container: a reusable image (template) that gets instantiated into a declarative spec (compose), composed of components (zones), and configured per-farm. This is the design pattern behind "design a new project from scratch".

Farm template

≈ Docker image

Reusable configuration bundle: default zones, governance, token economics, impact frameworks. A pre-built "Grant Application Template" ships with zones (production, nursery, biofactory) for funder-ready farms.

Farm specification

≈ docker-compose.yml

Declarative per-farm config — zones, governance, TE, ID, IF stored as JSONB on farm_specification.

Farm zones

≈ container components

Configurable zone types per farm: syntropic plot, agroforestry, biofactory, poultry, and more.

Needs · aspirations · objectives

≈ health checks / metadata

needs_assessment tracks community needs; stakeholder_aspiration formalizes wants; objective keeps hierarchical goals with auto-computed progress_pct.

Runtime topology

The whole platform runs as Docker Compose services. A notable detail: databases are private by default — you reach them via Compose service names, not published host ports. Image digests are pinned to @sha256 and CI fails on unpinned images.

databasePostgreSQL 16 + PostGIS
cacheRedis 7
directusAPI + permissions
clickhouseanalytics store
metabasedashboards · MCP
gatewayFastAPI · policy-aware · mobile
grpcport 50051 · streaming
caddyTLS · reverse proxy · /mobile → gateway
mosquittoMQTT · TLS 8883
🧱 Three container images: Dockerfile.worker (cron-based ingestion for scheduler jobs), Dockerfile.gateway (FastAPI gateway / Field Collector backend), and Dockerfile.grpc (Protobuf server with health checks).

Gateway routing at a glance: /health, /, /docs, and the Field Collector /mobile discovery routes are public; other routes are protected unless a deliberate resource/action/public policy says otherwise. Mobile sync authenticates with X-Device-Token; protected routes require x-api-key or x-capability-token. Caddy proxies /mobile* and /api/mobile/* to the gateway; other gateway /api/* routes stay on the gateway process (loopback 8099 in dev). A Directus bearer token is not gateway authentication.
